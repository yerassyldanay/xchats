# Үлес қосу

## Бастамас бұрын

- Алдымен ашық issue/PR-лардың қабаттаспайтынын тексеріңіз.
- Кішкентай түзетуден үлкенірек нәрсе үшін кодты жазбас бұрын өзгерісті
  сипаттайтын issue ашыңыз — жобада егжей-тегжейлі `plan/` каталогы бар
  ([`plan/DECISIONS.md`](../../../plan/DECISIONS.md) — жобалау шешімдерінің
  негізгі жазбасы), және тіркелген шешімге қайшы келетін өзгерісті алдымен
  сол жерде талқылау керек, ревью кезінде емес.

## Даму ортасын баптау

```bash
git clone https://github.com/yerassyldanay/xchats.git
cd xchats
make dev-backend     # backend :8080 портында (Go 1.25+)
make dev-frontend    # frontend :5173 портында (Node 22+, .nvmrc қараңыз)
```

`.env` файлы қажет емес, алдын ала баптайтын құпиялар жоқ — қараңыз
[`docs/release/installation.md`](../../release/installation.md). Екі
жергілікті процесті бөлек жүргізгіңіз келмесе, `make up` толық Docker
стегін іске қосады. Әдепкі әкімші аккаунтымен кіріңіз: `admin@xchat.kz` /
`xchat-admin-change-me` — бұл жария, құжатталған әдепкі құпия сөз (оны қалай
ауыстыру керектігін installation.md-дегі алғашқы іске қосу бөлімінен
қараңыз).

## PR ашпас бұрын

```bash
cd backend  && go build ./... && go vet ./... && go test -race -count=1 ./...
cd frontend && npm run typecheck && npm run test:unit && npm run build
make lint     # golangci-lint + eslint
```

Өзгерісіңіз `internal/httpapi`, `internal/kbstore`, `internal/responsestore`
немесе `internal/store` пакеттерін қозғаса, `make test-e2e` дерекқормен
жұмыс істейтін интеграциялық тест жиынтықтарын оқшауланған түрде іске
қосады.

**UI-ге қатысты өзгеріс** үшін тапсырманы аяқталды деп санамас бұрын оны
нақты браузерде тексеріңіз — тест жиынтықтары кодтың дұрыстығын тексереді,
бірақ фичаның дұрыс көрінетінін және дұрыс жұмыс істейтінін емес; нақты
нәтижеге көз жүгіртудің орнын ештеңе баса алмайды.

## Кодтағы конвенциялар (кодта бекітілген тәжірибе бойынша)

- **Backend:** Go, `internal/` пакет шекаралары архитектуралық
  тестермен бақыланады (`internal/dbtest.TestArchitectureBoundary`,
  `response.TestPackageDependencies`) — пакет құрылымдық тұрғыдан бармауы
  тиіс жерге барса, бұл тесттер CI-ге тең жергілікті жүргізуде сәтсіз
  аяқталады (мысалы, `internal/dbx`-ті тек анықталған пакеттер ғана тікелей
  импорттай алады). Айналып өтуден бұрын сәтсіз тесттің хабарламасын
  оқыңыз — әдетте ол дұрыс "тігісті" (wrapper әдісі, callback өрісі) өзі
  атайды.
- **Комментарийлер НЕГЕ екенін түсіндіреді, НЕ екенін емес.** Жақсы
  аталған функцияға оның атауын прозамен қайталайтын комментарий қажет
  емес. Комментарий анық емес шектеуді, инвариантты немесе кодтың
  күтілгеннен күрделірек көрінуінің себебін тіркегенде ғана орынды — келесі
  үш жолдың не істейтінін баяндау үшін емес.
- **Болжамды абстракциялар жоқ.** Алдыңыздағы есептің пішініне сәйкес
  келіңіз; әлі жоқ қажеттілік үшін жалпы қабат құрмаңыз.
- **Пакет деңгейіндегі әрбір жаңа мүмкіндік сол PR-де тестермен бірге
  келеді** — "кейін қосамыз" емес. Бұл кодтық база тестінің жиынтығы —
  тез өзгеретін аймақтағы байқалмайтын регрессияларға қарсы қорғаныс.
- **Frontend:** Vue 3 `<script setup>` + TypeScript, күй үшін Pinia,
  стильдеу үшін Tailwind, примитивтер үшін `reka-ui` (shadcn-vue үлгісі).
  en/ru кілттерінің қатаң паритетімен `vue-i18n` — аударма кілті бір
  локаль файлында бар да, екіншісінде жоқ болса, `locales.test.ts` құрылысты
  сәтсіз етеді; екеуін де бірден, сол PR-де қосыңыз, әрдайым.

## Commit хабарламалары

Бұл репозиторийдің тарихы `type: summary` конвенциясын ұстанады (`feat:`,
`fix:`, `refactor:`, `test:`, `docs:`, `chore:` — жалпы алғанда
[Conventional Commits](https://www.conventionalcommits.org/) пішінінде,
дегенмен бұл әзірге механикалық түрде тексерілмейді). Өзгерістің
*сипатына* сәйкес келетін типті таңдаңыз, summary-ді бұйрық райда жазыңыз
("add", "added" немесе "adds" емес), және тақырып жолын бір өзгеріске
шоғырландырыңыз — байланысты емес рефакторингті багты түзетумен араластыратын
PR екеуін де ревьюлеуді қиындатады және кейін таңдамалы түрде қайтаруды
мүмкін етпейді.

## Коммиттеріңізге қол қойыңыз (DCO)

Әрбір commit `Signed-off-by` трейлерін қамтуы керек, бұл сіздің оны
жазғаныңызды немесе оны осы жобаның лицензиясы бойынша ұсынуға құқығыңыз
бар екенін растайды ([Developer Certificate of
Origin](https://developercertificate.org/)):

```bash
git commit -s -m "fix: ..."
```

Бөлек CLA (Contributor License Agreement) жоқ. Backend-ке статикалық түрде
байланысатын GPL-3.0 лицензиялы тәуелділік `libsignal` (қараңыз
[`THIRD_PARTY_NOTICES.md`](../../../THIRD_PARTY_NOTICES.md)) контрибьюторлар
не қол қойғанына қарамастан, таратылатын бинарникті келешекте неғұрлым
рұқсат етуші лицензияға ауыстыру мүмкіндігін бәрібір жояды — сондықтан
болашақ перелицензиялау үшін CLA мұнда ешнәрсе бермейді. DCO мақсаты
тарлау, бірақ бәрібір нақты: әрбір жол [AGPL-3.0](../../../LICENSE)
лицензиясы бойынша осыны істеуге құқығы бар түрде қосылғанын білдіретін
анық, ауыртпалықсыз жазба.

## Pull request-тер

- PR-ларды бір өзгеріске шоғырландырыңыз — солай ревьюлеу оңайырақ, әрі
  бірдеңе дұрыс болмаса қайтару оңайырақ.
- PR сипаттамасында *неге* екенін түсіндіріңіз; *не* екені диффтан көрініп
  тұр.
- [`plan/DECISIONS.md`](../../../plan/DECISIONS.md) қамтитын аймаққа
  қатысты PR сол файлды сол PR-де жаңартуы керек, оны ескіруге қалдырмай.
- Әрбір PR мержден бұрын code owner-нен бір мақұлдаушы ревью талап етеді
  ([`CODEOWNERS`](../../../.github/CODEOWNERS)) — мейнтейнерлердің ешқайсысы
  өз PR-ын өзі мерж жасай алмайды.
- Ревью пікірлеріне жауап беріп отырыңыз; белсенділігі жоқ тасталған PR
  біраз уақыттан кейін жабылуы мүмкін және кейін әрқашан қайта ашылуы
  мүмкін.
