# Как внести вклад

## Перед тем как начать

- Сначала проверьте открытые issues/PR на предмет пересечения.
- Для чего-то большего, чем небольшое исправление, сначала откройте issue с
  описанием изменения — в проекте есть подробная директория `plan/`
  ([`plan/DECISIONS.md`](../../../plan/DECISIONS.md) — авторитетная запись
  проектных решений), и изменение, идущее вразрез с зафиксированным
  решением, нужно сначала обсудить, а не обнаруживать на этапе ревью.

## Настройка окружения разработки

```bash
git clone https://github.com/yerassyldanay/xchats.git
cd xchats
make dev-backend     # backend на :8080 (Go 1.25+)
make dev-frontend    # frontend на :5173 (Node 22+, см. .nvmrc)
```

Файл `.env` не нужен, секреты заранее настраивать не требуется — см.
[`docs/release/installation.md`](../../release/installation.md). Если не
хотите запускать два локальных процесса, `make up` поднимает весь стек в
Docker. Войдите под стандартной учётной записью администратора,
`admin@xchat.kz` / `xchat-admin-change-me` — это публичный, документированный
пароль по умолчанию (о том, как его сменить, см. пошаговое описание первого
запуска в installation.md).

## Перед тем как открыть PR

```bash
cd backend  && go build ./... && go vet ./... && go test -race -count=1 ./...
cd frontend && npm run typecheck && npm run test:unit && npm run build
make lint     # golangci-lint + eslint
```

`make test-e2e` запускает интеграционные наборы тестов с базой данных
изолированно — если ваше изменение затрагивает `internal/httpapi`,
`internal/kbstore`, `internal/responsestore` или `internal/store`.

Для **изменений, затрагивающих UI**, перед тем как считать задачу
выполненной, проверьте его в настоящем браузере — наборы тестов проверяют
корректность кода, а не то, что фича выглядит и ведёт себя правильно; ничто
не заменит взгляд на реальный результат.

## Соглашения по коду (по факту принятые в кодовой базе)

- **Backend:** Go, границы пакетов `internal/` контролируются
  архитектурными тестами (`internal/dbtest.TestArchitectureBoundary`,
  `response.TestPackageDependencies`) — они падают при локальном запуске,
  эквивалентном CI, если пакет структурно обращается туда, куда не должен
  (например, только определённым пакетам разрешено напрямую импортировать
  `internal/dbx`). Сначала прочитайте сообщение упавшего теста — обычно оно
  само называет правильный «шов» (обёрточный метод, поле-колбэк) вместо
  обхода проверки.
- **Комментарии объясняют ПОЧЕМУ, а не ЧТО.** Хорошо названная функция не
  нуждается в комментарии, пересказывающем прозой её название. Комментарий
  оправдан, когда фиксирует неочевидное ограничение, инвариант или причину,
  по которой код выглядит сложнее, чем ожидалось — а не когда пересказывает,
  что делают следующие три строки.
- **Никаких умозрительных абстракций.** Решайте задачу, которая перед вами,
  а не стройте общий слой под потребность, которой пока нет.
- **Каждая новая возможность на уровне пакета получает тесты в том же PR**
  — не «добавим позже». Набор тестов этой кодовой базы — это защита от
  незаметных регрессий в быстро меняющейся области.
- **Frontend:** Vue 3 `<script setup>` + TypeScript, Pinia для состояния,
  Tailwind для стилей, `reka-ui` (паттерн shadcn-vue) для примитивов.
  `vue-i18n` со строгим паритетом ключей en/ru — `locales.test.ts` роняет
  сборку, если ключ перевода есть в одном файле локали, но отсутствует в
  другом; добавляйте оба сразу, в одном PR, каждый раз.

## Сообщения коммитов

История этого репозитория следует соглашению `type: summary` (`feat:`,
`fix:`, `refactor:`, `test:`, `docs:`, `chore:` — в целом в духе
[Conventional Commits](https://www.conventionalcommits.org/), хотя
формально это пока не проверяется автоматически). Выбирайте тип, отражающий
*природу* изменения, пишите summary в повелительном наклонении («добавить»,
а не «добавлено» или «добавляет»), и держите строку темы сфокусированной на
одном изменении — PR, смешивающий несвязанный рефакторинг с исправлением
бага, усложняет ревью обоих и делает невозможным выборочный откат позже.

## Подписывайте коммиты (DCO)

Каждый коммит должен содержать трейлер `Signed-off-by`, удостоверяющий, что
вы его написали или иначе имеете право отправить его под лицензией этого
проекта ([Developer Certificate of
Origin](https://developercertificate.org/)):

```bash
git commit -s -m "fix: ..."
```

Отдельного CLA (Contributor License Agreement) нет. `libsignal` —
зависимость с лицензией GPL-3.0, статически линкуемая в backend (см.
[`THIRD_PARTY_NOTICES.md`](../../../THIRD_PARTY_NOTICES.md)), — уже
исключает возможность когда-либо перелицензировать распространяемый
бинарник на более разрешительную лицензию, независимо от того, что подпишут
контрибьюторы, — так что CLA ради будущего перелицензирования здесь ничего
не даёт. Цель DCO более узкая и по-прежнему реальная: чёткая,
необременительная запись о том, что каждая строка внесена с правом сделать
это по лицензии [AGPL-3.0](../../../LICENSE).

## Pull request'ы

- Держите PR сфокусированными на одном изменении — так проще ревьюить и
  проще откатить, если что-то не так.
- Объясняйте *почему* в описании PR; *что* уже видно из диффа.
- PR, затрагивающий территорию, покрытую
  [`plan/DECISIONS.md`](../../../plan/DECISIONS.md), должен обновлять этот
  файл в том же PR, а не оставлять его устаревать.
- Каждый PR требует одобряющего ревью от code owner перед мержем
  ([`CODEOWNERS`](../../../.github/CODEOWNERS)) — ни один из мейнтейнеров не
  может смержить свой собственный PR.
- Реагируйте на замечания ревью; заброшенный PR без активности может быть
  закрыт через некоторое время и всегда может быть открыт заново позже.
