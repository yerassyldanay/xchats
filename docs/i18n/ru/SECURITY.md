# Политика безопасности

## Как сообщить об уязвимости

**Не создавайте публичный GitHub issue для уязвимости безопасности.**

Сообщайте приватно через [приватное сообщение об уязвимости на
GitHub](https://github.com/yerassyldanay/xchats/security/advisories/new)
(вкладка **Security** этого репозитория → **Report a vulnerability**).

По возможности укажите:

- Тип проблемы (например, утечка учётных данных, обход авторизации,
  инъекция, отказ в обслуживании).
- Шаги для воспроизведения или proof of concept.
- Версию/коммит, на котором проверяли.
- Понимание воздействия — что реально мог бы сделать атакующий.

## Чего ожидать

xchats поддерживается небольшой командой без выделенного специалиста по
безопасности, поэтому честная базовая линия — это работа по мере
возможности, а не выполнение формального SLA:

- **Подтверждение получения:** в течение 5 рабочих дней.
- **Первичная оценка** (подтверждено / не уязвимость / нужны уточнения): в
  течение 10 рабочих дней.
- **Сроки исправления:** сообщаются после оценки серьёзности — критичные
  проблемы (удалённая утечка учётных данных/данных, обход авторизации)
  приоритизируются над всем остальным, что в работе.

## Область действия

**В рамках:**

- Go-сервис `backend/` и Vue-приложение `frontend/` в том виде, в каком они
  собираются из этого репозитория.
- Docker-образы в `deploy/` в опубликованном виде (если/когда они
  опубликованы — см.
  [`docs/release/release-checklist.md`](../../release/release-checklist.md)).

**Вне рамок:**

- Уязвимости в самих сторонних зависимостях — сообщайте о них
  разработчикам этих зависимостей (список — в
  [`THIRD_PARTY_NOTICES.md`](../../../THIRD_PARTY_NOTICES.md)), хотя сообщение
  о том, как именно xchats *использует* уязвимую версию зависимости, —
  приветствуется.
- Операционная безопасность конкретного развёртывания (непропатченная ОС,
  открытый порт базы данных, никогда не сменённый bootstrap-пароль
  администратора — см. [`docs/release/installation.md`](../../release/installation.md),
  почему это нужно сделать) — это ответственность оператора, а не уязвимость
  самого xchats, хотя пробелы в документации, из-за которых небезопасная
  настройка по умолчанию становится более вероятной, — сообщать можно и
  нужно.
- Социальная инженерия, физический доступ или отказ в обслуживании против
  сторонней инфраструктуры (ngrok, LLM-провайдеры, API GitHub), которую
  xchats лишь использует.

## Поддерживаемые версии

Пока не существует стабильной истории релизов, поддерживаются только
последняя выпущенная версия и `master`. Этот раздел будет обновлён, когда
появятся тегированные релизы — см.
[`docs/release/release-checklist.md`](../../release/release-checklist.md).

## Известные, осознанные компромиссы безопасности (не уязвимости)

Фиксируем их заранее, чтобы они не поступали повторно как находки — каждый
пункт это явное, задокументированное проектное решение, а не недосмотр:

- **Туннель ngrok обслуживает всё приложение, а не только allowlist
  API-путей** — включая страницу входа — пока активен. Зафиксировано как
  проектное решение; смягчается тем, что cookie получают флаг `Secure` через HTTPS
  туннеля, и явным предупреждением в интерфейсе перед запуском. См.
  [`docs/release/troubleshooting.md`](../../release/troubleshooting.md).
- **Хранилище учётных данных на файлах слабее, чем OS keychain** — оно
  зашифровано на диске, но без контроля доступа на уровне ОС, и требует
  явного включения (`XCHATS_ALLOW_FILE_CREDENTIALS=1`) плюс подтверждения в
  интерфейсе перед использованием. См.
  [`docs/release/credentials.md`](../../release/credentials.md).
- **Учётные данные администратора по умолчанию (`admin@xchat.kz` /
  `xchat-admin-change-me`) — это публичный, общий для всех пароль по
  умолчанию** — он указан в README и зафиксирован в истории миграций этого
  репозитория, восстанавливается при каждой свежей установке ради удобства
  self-host-развёртывания. Принудительной смены пароля при первом входе
  больше нет: развёртывание, где этот пароль никогда не меняют, открыто для
  любого, кто прочитал документацию, и смена пароля — ответственность
  оператора, а не то, что обеспечивает сам xchats. `xchats
  reset-admin-password` восстанавливает этот же пароль по умолчанию, если
  изменённый пароль когда-либо потерян. Описано в
  [`docs/release/installation.md`](../../release/installation.md).

## Подключение к WhatsApp

xchats подключается к WhatsApp через [whatsmeow](https://github.com/tulir/whatsmeow) —
неофициальный, реверс-инжиниринговый клиент, а не официальный WhatsApp
Business API. Это осознанный компромисс продукта, а не уязвимость, но у
него есть реальные последствия, которые стоит проговорить прямо: WhatsApp
может заблокировать подключённый номер по своему усмотрению, без
возможности оспорить. Не подключайте номер, потерю которого не готовы
принять.
