# Definition of Done — per phase

Acceptance criteria for each build phase from `0-overview.md`. A phase is **done** only when its
checklist passes — verified by the isolated harness in `6-isolated-testing.md` (no real WhatsApp).
Each phase builds on the previous. **v1 is the minimal vertical slice** (Login + Chatboard, text-only,
single pre-connected account, on-demand drafts, no auto-send); everything marked *deferred* below is
v2+ — designed, not built.

## Phase 0 — Prerequisites (blocking gate; do before estimating Phases 2 & 4A)

Three inputs that Phases 2 and 4A *depend* on — so they are a gate, not footnotes. Done when:
- **Brain submodule verified.** `git submodule status` shows it initialized (it now is) **and**
  `cd plan/examples/repos/xpayment-crm && go test ./...` passes, and reuse/licensing is confirmed. If
  this fails, the AI is a *build*, not a *port* — re-scope before committing to Phase 4A.
- **Captures recorded.** ✅ Done — inbound `messages.upsert` (text / image / image+caption), the
  outbound send fixtures (`sendText`/`sendMedia`/`sendSticker`), and a matched
  `send.message`→`messages.update` pair are in `captures/`. Status correlation is settled
  (`messages.update.keyId == evolution_message_id`, see `captures/README.md`).
- **KB seeded (non-empty).** Pick the first pilot org and seed a published Snapshot — reuse
  `0002_seed.sql` or mine ~100 of the org's real chats (the same corpus seeds the golden set). An
  empty KB makes every draft a useless escalation (see `8-ai-assistant.md` → Knowledge Base).

Verify: the submodule's tests pass; the matched capture pair is committed under `captures/`; a
non-empty Snapshot loads on boot.

## Phase 1 — Foundation (runnable skeleton)

Done when:
- The monorepo exists: `backend/` (Go module) + `frontend/` (Vue/Vite) + `deploy/` (compose +
  optional `postgres.compose.yaml` / `redis.compose.yaml` + Makefile) + single `.env(.example)` /
  `config.yaml(.example)`.
- `make up` starts the stack against the **reused** Postgres by default; `make up-local` runs it
  against the optional local datastore composes — switching is **env-only** (no code change).
- Backend boots, connects to Postgres, **applies migrations** (all `xchats.*` tables from
  `9-database-schema.md`), and serves `GET /healthz` (200) and `GET /readyz`.
- The **Evolution bootstrap** runs idempotently: ensures the instance + sets the webhook to
  `/evolution/api/v1/webhook/{account}` with the shared token; re-running is safe.
- Seed: `config.yaml` users + default org are **upserted** on startup; login works
  (`POST /xchats/api/v1/auth/login` → session; `GET /me` returns the user+org).
- Frontend serves on its own port and reaches the backend via `API_BASE_URL`.

Verify: `make up` healthy + tables present; `make up-local` works with no code change; bootstrap
logs show `webhook/set` succeeded; login round-trips.

## Phase 2 — Backend transport (the core loop)

**Captures (done — Phase 0):** the inbound `messages.upsert` (text / image / image+caption), the
outbound send fixtures, and a matched `send.message`→`messages.update` pair are committed under
`captures/`. Status correlation is **settled**: `messages.update.data.keyId` equals the message's
`evolution_message_id` (see `captures/README.md` finding 4). Still uncaptured (nice-to-have, not
blocking): `getBase64FromMediaMessage` (media phase) and `connection.update` / `qrcode.updated`.

Done when (all via the **fake Evolution + `captures/` fixtures**, `make test-e2e`):
- Webhook edge: enqueues the raw event to the in-memory queue, returns 200 fast (no DB write); a
  worker upserts; a **replayed event is a no-op** (idempotent on `UNIQUE(account_id, evolution_message_id)`).
- Normalizer parity: output matches `scripts/evolution_client.py` for the same fixtures
  (text + media, `@lid`↔phone via `remoteJidAlt`, status 0-5).
- Inbound `messages.upsert` → upserts `xchats.wa_contacts`, `xchats.wa_chats` (keyed on phone),
  `xchats.wa_messages`; **no duplicates** on replay.
- Media (v1 = placeholder): an inbound `imageMessage` stores the message + `message_kind` with the
  caption (if any) and renders as a "media received" placeholder — **no download in v1**. (The actual
  `getBase64FromMediaMessage` pipeline → `xchats.message_media` `dl_state` is deferred to Phase 4C; the
  response is still captured in Phase 0 so it's ready.)
- Outbound: `POST /xchats/api/v1/chats/{id}/messages` → the handler calls Evolution `sendText` →
  fake Evolution receives a send **to the phone, not the `@lid`**; `evolution_message_id` stored.
- Status: replayed `messages.update` moves `delivery_state` `sent → delivered → read`
  **monotonically** (a late event never downgrades). Correlation is **settled by capture**: match
  `messages.update.data.keyId` → `wa_messages.evolution_message_id` (verified equal in the fixtures,
  v2.3.7 — no separate correlation column needed; see `captures/README.md` finding 4).
- Responses follow the `{payload, errcode}` envelope + status mapping in `7-api-contracts.md`.

Verify: `make test-e2e` green; the full inbound→store and send→status loops assert against fixtures —
including the **matched send→update pair**, so the status correlation is proven, not assumed.

## Phase 2.5 — AI dry-run (de-risk the differentiator early)

A thin slice that proves the suggestions are useful **before** building the full UI. No inbox UI
required. Done when:
- The decoupled `HandleMessage` + `Drafter` + a **new Postgres Window/Profile reader** are ported
  (the brain logic is unchanged — see `8-ai-assistant.md` → *Porting*).
- Running an inbound `captures/` fixture (or the Playground wired to Phase-2 normalized rows) against
  a **non-empty published Snapshot** produces a `Draft` that is dumped to a log / minimal view.
- A handful of golden questions (`8-ai-assistant.md` → *Evals*) produce **grounded, non-escalating**
  drafts — i.e. the wedge demonstrably works, not "a row was produced".

Verify: a fixture chat + a seeded KB yields a readable, correct draft in the log; an
off-KB question escalates. (This is the earliest honest answer to "is the AI any good?".)

## Phase 3 — UI (slice: Login + Chatboard)

v1 ships **two pages only** — Login and Chatboard — against a **single pre-connected** account.
Done when:
- Login works; the app lands on the Chatboard. (The multi-account **WhatsApp accounts** manager —
  list/assign/unassign, Add-account QR flow — is **deferred**; v1 uses one account from config.)
- Chatboard: chat list, chat view with inbound/outbound bubbles + **delivery/read ticks**,
  composer (send **text**; inbound media renders as a placeholder), and the **AI draft card** in the
  right panel (draft + contact mini-profile only — no Auto-responder, no Interaction-history panel).
- Live updates over **SSE** (`message.*`, `chat.*`, `ai_draft.generating`, `ai_draft.created`, `ai_draft.updated`).
- The UI talks **only** to `/xchats/api/v1` (+ realtime); same flows pass against the fake backend.

Verify: component tests (Vitest) pass; an e2e drives login → see a fixture message live → Suggest →
edit/approve → send → tick updates. (Connecting a **real** number is a manual smoke outside isolation.)

## Phase 4A — AI draft loop (v1)

The v1 AI is the **draft loop only**, in adapter mode (text-only, one seeded Snapshot, **on-demand**
trigger, no media refs, no admin UI, no playground, no auto-send — see `8-ai-assistant.md` →
*v1 adapter mode* / *Porting*). Done when (per `8-ai-assistant.md` → *Port gate*):
- The brain is ported; `go test ./internal/assistant/...` passes after the module-path rewrite.
- A seeded Snapshot is loaded into Postgres (`xchats.ai_*`) from `0002_seed.sql`/markdown on boot — no
  admin editing UI required.
- On the user pressing **"Suggest reply"** (on-demand), the `ai_draft` task runs `HandleMessage` →
  writes **one `rp_suggestions` row** (1–3 options in `jsonb`, media nested) + emits `ai_draft.created`; the UI shows the **1–3
  options**; **approve the chosen one → sends** via the Phase-2 pipeline (`sender_kind='ai'`). Approve
  is **idempotent** (one send per suggestion; siblings superseded; a stale/consumed suggestion returns
  a conflict — see `7.1-endpoints.md`).
- Guardrails honored: facts are tokens `{{table.slug.field}}` until injected; an option may carry **media from the seeded
  asset catalog**, rendered as **detachable** chips (attaching a *new* file needs the asset-catalog UI
  — deferred, Phase 4B); reply in the customer's language; **no auto-send** (the `respond_mode` auto
  path is not built).
- **KB is seeded (not empty)** — the Phase-0 gate. The brain answers **only** from the published
  Snapshot and escalates on any gap; an empty KB makes *every* draft a useless escalation.
- **Answer quality is gated, not just plumbing.** The golden set + deterministic metrics
  (`8-ai-assistant.md` → *Evals*) pass: held-out real questions produce **grounded, non-escalating** drafts.
- **Compliance gate (before any real customer send — not before isolated tests):** the lawful basis
  for sending chat text to the LLM is decided and documented (in-region/self-host via `LLM_BASE_URL`,
  or consent + PII minimization + a DPA), plus a retention/deletion stance. See `8-ai-assistant.md`
  and `2-architecture.md` (Security). Isolated Phases 1–4A build/test are **not** blocked by this.

Verify: against a **non-empty** seeded Snapshot, pressing Suggest on an inbound fixture produces a
*grounded* draft (not an escalation) and the golden set passes; an off-KB question correctly escalates;
approve-draft round-trips to a sent message with status updates. (A bare escalation row does **not**
satisfy this.)

## Phases 4B–4D — deferred (designed, not built in v1)

Re-staged out of v1; the design stays in `8.*` / `9-database-schema.md`. Build by real pain after the
slice proves the loop.
- **4B — KB admin & evals UI:** the persona/topics/assets/prices CMS, draft→publish→rollback, the
  Playground, and `POST /assistant/publish` gated on the eval bar (fact-safety / asset-precision).
- **4C — media & facts:** inbound media download/transcription, suggested/outbound media (`asset_refs`
  rendered), the typed fact-tables editor (tariffs/products/contacts/policies).
- **4D — auto-send:** `respond_mode = CONFIGURE_TIME | ALWAYS` and its send path, behind the
  confidence/golden-gate preconditions in `8-ai-assistant.md` → *Wiring* (incl. the grounding judge,
  mandatory before auto-send per record 14). Not built in v1.

## Global "ready" bar

v1 is **delivered** when Phase 0 (prerequisites) and Phases 1–4A are individually done **and**
`make test-e2e` runs the whole slice green in an isolated environment from one command, plus one
manual real-Evolution smoke (`localhost:9700`) confirming live connectivity. Phases 4B–4D and the
deferred surfaces (multi-account, media, CMS) are explicitly **out** of the v1 bar.
