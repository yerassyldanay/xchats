# KB Builder — the builder agent

The LLM agent that turns chat turns (text, notes, links, files) into a reviewed draft Snapshot. It is a
**different job from the runtime brain** (`8-ai-assistant.md`): the brain *answers customers* from a
frozen snapshot; the builder *edits the draft snapshot* via tools and asks the operator when unsure.
They **share the LLM client and `LLM_*` env** (provider-neutral, OpenAI-compatible tool calling) but
have different prompts, tools, and loops. Lives in `backend/internal/assistant/builder`.

## Hard separation from the brain

| | Runtime brain | Builder agent |
|---|---|---|
| Reads | the **published** snapshot (immutable, in-memory) | the **draft** snapshot rows (DB) |
| Writes | nothing (caller persists drafts) | the **draft** via tools (proposed rows / changesets) |
| Output | one forced `emit_draft` per message | a turn of **tool calls** + a short chat reply |
| Can it reach a customer? | only via human-approved send | **never** — four gates away (`11`, §8) |
| Trigger | "Suggest reply" | an operator message / a resolved request |

---

## The loop (one agent run)

A run is enqueued by `POST …/messages` or by resolving a request. It is **bounded** (≤ N tool calls per
run; default 8) and **cannot block** on a human.

```text
1. CONTEXT   build the prompt: [system] + [draft digest] + [recent transcript] + [new input(s)]
2. NORMALIZE any attachment without text is normalized first (URL/PDF → text; media → describe_media)
3. THINK+ACT the model emits tool calls (below). The runner executes each, collecting results.
4. ROUTE     each effect goes to its path:
               low-stakes  → apply to draft now, row.review_state='proposed'   (+ builder.draft.updated)
               high-stakes → buffer into an OPEN changeset (diff card)          (+ builder.changeset.created)
               unsure      → emit a request (popup), create NO row             (+ builder.request.created)
5. REPLY     the model writes one short chat turn: what it did + what it needs next.
6. END       the run ends. Resolving a request/applying a changeset enqueues the NEXT run with that result.
```

The **draft digest** (step 1) is a compact view — block titles + first line, the topic list with slugs
+ keywords + asset counts, the price tokens, and the count of open requests/changesets — **not** the
full bodies. This keeps the prompt cheap and lets the agent decide "new topic vs. append" and "duplicate?"
without loading everything. (Full bodies are fetched by the `read_topic` tool only when needed.)

## Tool catalog

Tools are the agent's only way to change anything. Each tool's **route** (direct / changeset / request)
is fixed by the safety rules in `11`, §5 — the model can't choose to bypass review.

| Tool | Args | Route | Effect |
|---|---|---|---|
| `read_topic` | `slug` | read | returns full `body_md` + assets (to decide append vs. new) |
| `search_kb` | `query` | read | keyword match over the draft (dedup / "where does this go?") |
| `upsert_topic` | `slug, lang, keywords, body_md` | **direct** (proposed) | create/append a topic; prices as `{{tokens}}` |
| `attach_asset` | `ref, kind, topic_slug, description, blob_id\|url` | **direct** (proposed) | add a media/link asset to a topic |
| `set_block` | `key('identity'\|'goal'\|'quality'\|'support'), body` | **changeset** | propose a config-block edit (diff) |
| `propose_price` | `token, amount_text?, evidence` | **changeset + request** | add a price op **and** a `confirm_price` popup |
| `merge_topics` / `merge_assets` | `from, into` | **changeset** | structural merge (diff) |
| `delete` | `kind, ref, reason` | **changeset** | propose a deletion (diff) |
| `open_changeset` | `title, summary` | — | start a diff bundle; subsequent block/price/delete/merge ops attach to it |
| `request_review` | `changeset_id` | — | finalize the open changeset → emits the diff card |
| `ask` | `req_type, prompt, context, target` | **request** | raise a popup (describe_media / choose_topic / resolve_duplicate / comment) |
| `say` | `text` | — | the chat reply to the operator (always the last call) |

> **Why prices are both:** `propose_price` writes the **op** (so the diff shows the number changing)
> *and* a `confirm_price` request (so a human must accept the digit). The changeset's `needs[]` lists
> the request, and **apply is blocked until it's resolved** — the number can't slip in unreviewed.

The runner validates every call (known slug/ref/kind, token format `^[a-z]+\.[a-z_]+$`, blob_id exists,
no digits in `body_md` where a token belongs) and rejects malformed calls back to the model as a tool
error, so a bad call is self-correcting, never a bad row.

## Proactive policy — "behave proactively" made concrete

The brief wants a builder that *asks when ambiguous, suggests improvements, and keeps the KB clean.*
That is a set of **rules in the system prompt + runner checks**, not vibes:

1. **Ask, don't guess (the core rule).** If a fact needed to write a row is missing or ambiguous —
   *what a media file shows, which topic it belongs to, a price's exact value, whether two topics are
   the same* — emit an `ask`/`confirm_price`/`resolve_duplicate`/`choose_topic` **instead of** writing a
   row. A wrong guess costs a rejected diff; an honest question costs one tap.
2. **Never invent numbers.** Any price/limit → a `{{token}}` in prose + `propose_price` (→ `confirm_price`).
   The model is told the price book is the *only* place a digit lives.
3. **Append, don't fork.** Before creating a topic, `search_kb` for an existing one; a new tariff image
   **appends** to `tariffs` rather than spawning `tariffs_2`. Overlap → `resolve_duplicate`.
4. **Every asset earns its description.** An asset with an empty/weak description is not "done" — the
   agent raises `describe_media` (with the thumbnail) rather than ship a blind selection cue.
5. **Suggest improvements (gently, as the `say` turn or a `comment` request).** After acting, the agent
   surfaces gaps it noticed: *"You have no topic for refunds — customers often ask. Want to add one?"*,
   *"The pricing page link is 6 months old — still current?"*, *"This video has no text summary, so I
   can attach it but can't answer from its content — paste 2–3 key points?"* These are **suggestions,
   never silent edits**.
6. **Coverage hint at publish.** Before publish the editor shows a small checklist (blocks filled?
   topics for the org's top questions? every asset described? every token priced?) — derived, not
   nagging.

The policy is **tuned by examples in the prompt**, and its decisions (ask vs. act) are testable offline
with fixture transcripts (`11.5`) — no live LLM needed to assert "an undescribed image produced a
`describe_media`, not a blank asset".

## Normalization — drive every input to text (then structure)

The model reasons only over **text**, so every input is first normalized. One `Normalizer` interface
with a per-source implementation and an **always-available fallback: ask the operator** (so the system
is fully chat-driven from day one, with auto-extraction dropping in later behind the same UX).

```go
type Normalizer interface {
    // returns extracted text, or signals that a describe_media request is needed
    Normalize(ctx, attachment) (text string, needDescription bool, err error)
}
```

| Input | Normalize step (v1) | Fallback when hard/costly |
|---|---|---|
| **Plain text / note** | use directly → topic body / block | — |
| **Link / URL** | fetch (existing HTTP client, allow-listed schemes, size+timeout cap) → extract main content (readability) → summarize | `comment`/`ask`: "paste the key points" |
| **PDF / doc** | extract text (`pdftotext`/a Go lib) → the agent splits into topics, asks which sections matter | `ask`: "which sections matter?" |
| **Image / infographic** | **`describe_media`** popup (operator describes what + when) | — (this *is* the v1 path) |
| **Video / audio** | **`describe_media`** popup + keep the file/URL | — |

> **Scope (from the brief):** auto-extraction of media is **optional and phased**. v1 does **text + URL
> + PDF** auto-structuring and **operator-described media**. Later, vision-captioning and transcription
> run in the normalize step and **pre-fill** the same `describe_media` popup (the operator confirms
> instead of writes) — **no UX or schema change**. The seam is the `Normalizer` port + the
> `needs_description` attachment state.

Normalization runs as a **queue job** (`ai_builder` task family) so a slow fetch/extract never blocks
the request; the attachment's `norm_state` is the durable status, and `builder.attachment.updated`
tells the UI when a file flips to `needs_description` or `normalized`.

### Media-as-knowledge (when the file's *content* should be answerable)

For a knowledge-bearing image/video (a how-to, an infographic with facts), the agent does **two**
things (the rule from `8-ai-assistant.md`): `attach_asset` for the bytes **+** `upsert_topic` for a
companion text topic (`body_md` = an answer-shaped ~80–150-word summary, linked by `topic_slug`). The
**asset description** is the *selection cue*; the **topic body** is what the brain *answers from*. In
v1 that summary comes from the operator (via the popup); later, from transcription/vision.

## Cost, determinism, and safety

- **Cheap context.** Send the **digest**, not the whole KB; fetch full bodies via `read_topic` only when
  appending/merging. Cache the system prompt prefix (stable per session).
- **Bounded runs.** ≤ 8 tool calls/run; the runner stops and replies if exceeded (the operator can say
  "continue"). Prevents runaway loops/spend.
- **Low temperature** for structuring; the output that matters is *structured tool calls*, parsed
  defensively (tool-call API, with a JSON-in-content fallback like the brain).
- **The agent never publishes.** Publish is a separate, explicit human action through the gate
  (`11.2`). The agent can *suggest* "ready to publish?" but cannot trigger it.
- **Everything is provenance-stamped** (`source`, `ref`, `session_id`) so every row/op traces to the
  chat message, URL, or file that produced it — shown in the diff and editor.
- **Tenant-scoped.** A session is bound to one org's draft; tools can only read/write that draft. The
  builder honors the same **LLM data boundary** as the brain (`2-architecture.md`) — though it ships
  *operator-authored business content*, not customer PII, so the cross-border concern is lighter.

## Pseudocode — the runner

```go
func RunBuilderTurn(ctx, sessionID, userMsg) error {
    draft := store.LoadDraftDigest(sessionID)            // compact view
    for _, att := range userMsg.Attachments {            // normalize first
        if text, needDesc, _ := normalizer.Normalize(ctx, att); needDesc {
            raiseRequest(describe_media, att)             // popup, no row
        } else { att.ExtractedText = text }
    }
    msgs := buildPrompt(systemPrompt, draft, transcriptTail, userMsg)
    for i := 0; i < maxToolCalls; i++ {
        out := llm.Chat(ctx, msgs, builderTools)          // OpenAI-compatible tool calling
        if out.Say != "" { persistAssistant(out.Say); break }
        for _, call := range out.ToolCalls {
            res := dispatch(call)                          // route: direct | changeset | request
            msgs = append(msgs, toolResult(call, res))     // feed result back
        }
    }
    emitSSE()                                              // builder.message / .changeset / .request
    return nil
}
```

The dispatch table is the single place the **route** (direct vs. changeset vs. request) is enforced, so
the safety model lives in code, not in the model's discretion.
