# AI Assistant — Knowledge Base

How the curated knowledge that grounds the brain is organized. It is the **only** source the model
may answer from. Implementation: the `Snapshot` in
`examples/repos/xpayment-crm/internal/domain/` (`catalog.go`, `draft.go`), rendered into the prompt
by `internal/usecase/assistant/prompt.go` (blocks `[D]` and `[E]`).

## Two lanes — Facts vs Knowledge

The KB holds **two kinds of information**, handled differently — this split *is* the anti-hallucination
strategy (see `11-ai-design-overview.md` and the decision record `13-kb-facts-and-grounding`):

- **Facts** — prices, tariffs, limits, times, hours, addresses, phones. **Exact, verbatim.** They live in
  **typed tables with concrete columns** (`ai_tariffs`, `ai_products`, `ai_contacts`) and code substitutes
  the stored value; the model **never writes the number**. A fabricated specific is impossible by
  construction.
- **Knowledge** — policies, descriptions, how-things-work. **Faithful paraphrase.** It lives as prose in
  `ai_topics`; the model writes it and a **grounding judge** checks that every claim is supported.

Exact things are never authored by the model; explanatory things are authored but checked.

## A published **Snapshot** = config + topics + media catalog + typed facts

It is edited in the admin UI, **versioned**, and **published**; the live snapshot is what the
prompt is built from. (Editing produces a draft; publish swaps the live snapshot atomically;
rollback restores a prior version.)

### Config (identity & rules)

`persona`, `mission`, `guardrails`, `language_policy` — these become prompt blocks `[B]`/`[C]`.

### Topics — the textual KB — the **Knowledge lane** (`[D]`)

Each topic has: `slug`, `language`, `keywords`, `body` (markdown). Rendered as
`# topic: <slug> (<language>)` + keywords + body. Keep topics small and answer-shaped; the model
answers **only** from these. **Links** belong in the topic body (markdown) and the model includes
them in the reply when relevant.

### Media catalog — assets (`[E]`)

Each asset has: `ref` (stable id used in `asset_refs`), `kind` (`image | video | document | audio`),
`topic` (the slug it supports), `description` (what it is / when to send), and a `url` (resolved at
send time by the media store). Rendered as `ref | kind | topic | description`.

- The model selects assets **by `ref`** (max 3); only catalog refs resolve (`ResolveAssets`), so it
  cannot attach anything not curated.
- **Images and video** are assets like any other (`kind=image|video`) with a clear `description`
  so the model knows when to attach them; the bytes are served by xchats' media store
  (local disk → object storage; see `2-architecture.md`).

### Facts — **typed tables; tokens, not numbers** — the **Facts lane**

Every exact fact is a **column on a typed table** (`ai_tariffs`, `ai_products`, `ai_contacts` — see
`9-database-schema.md`), stored **verbatim with units**. In topic bodies and in replies it is referenced
only as a token `{{table.slug.field}}` (e.g. `{{tariff.growth.price}}`, `{{tariff.growth.limit_text}}`,
`{{contact.support.whatsapp}}`); code substitutes the stored value **for the reply's language** after
drafting. **Language is a row, not a column** — one row per `(entity, language)`, a `*` row for
language-neutral values — so a new language is new rows, not new columns. The old generic value bag
`ai_values` is **removed** (a nearest-key lookup can return the *wrong* tariff). **Fail closed:** an
unresolved token never ships — it becomes a holding reply for manual review. This keeps facts correct,
centrally editable, and **impossible for the model to invent**.

## Seeding a new org's KB (cold start) — the load-bearing first task

The brain answers **only** from this KB. An **empty KB therefore makes every draft an escalation** —
the product does nothing useful on day one. So seeding the KB is not optional polish; the working
brain's own roadmap calls mining real conversations to seed the KB (and the golden set) *the
load-bearing first task*. xchats must carry it, not just the editing UI.

- **Who + what:** name the first org and the domain its KB covers (record it; see
  `0.1-definition-of-done.md` Phase 4). Decide explicitly: **reuse** the existing xpayment-crm KB, or
  **mine this org's own ~100 recent chats** into a starter topic list + typed fact tables + media catalog.
- **Starter snapshot:** carry the submodule's `migrations/0002_seed.sql` (a minimal *published*
  persona/topics/facts/assets so the service boots usable) into the Postgres `xchats.ai_*` tables on
  first boot — so the admin opens onto a working example to edit, not a blank form (see
  `8.6-port-checklist.md`).
- **Day-one runtime state is safe but useless:** before a KB exists the brain escalates everything
  (suggest-only, so nothing wrong reaches a customer). The point is to get *out* of that state — a
  published Snapshot with coverage of the org's top questions — before exposing the assistant.
- **Quality bar before exposure:** a held-out set of real questions should produce grounded,
  non-escalating drafts (the golden set in `8.7-ai-evals.md`), not just "a row was produced".

## Why curated (not vector RAG) — for now

The KB is small and hand-curated, so it fits directly in the prompt → deterministic, cheap, and
controllable, with no retrieval errors. When it outgrows the prompt, add **pgvector** retrieval
(top-k per message) behind the same context port — in the same Postgres — without changing the
brain. See `8-ai-assistant.md`. Note this applies to the **Knowledge** lane only: **facts are never
retrieved by similarity** — a nearest-neighbor can return the wrong tariff — they resolve by exact
`{{table.slug.field}}` lookup (decision record `13`).
