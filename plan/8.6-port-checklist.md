# AI Assistant — Port Checklist

How to port the working brain from the submodule (`examples/repos/xpayment-crm/`) into the xchats
backend. The brain logic is reused **as-is**; only the edges change (Chatwoot → xchats Postgres,
SQLite → Postgres, draft → `xchats.ai_drafts`). Reference: `examples/repos/xpayment-crm/IMPLEMENTATION.md`.

> **v1 adapter mode:** port the brain but run the **minimal slice** — text-only drafts, one seeded
> Snapshot (no CMS), **on-demand** trigger, no media refs rendered, no auto-send (see
> `8-ai-assistant.md` → *v1 adapter mode*). The "Reuse as-is" rows below are still copied; the
> **adminui** row and the **publish gate** are deferred to **Phase 4B** for UI exposure.

## What changes vs. what stays

The brain's core is decoupled by ports: `assistant.HandleMessage(ctx, ChatID, inbound) -> Draft`
reads via a conversation/profile reader, drafts via an LLM `Drafter`, and **writes nothing** — the
caller persists. So the port is small: swap the reader + the persistence side, keep everything else.

## Adapt

| Item | Action |
|---|---|
| The conversation/profile reader port (in the submodule, `ChatwootReader` with `Window` + `Profile`) | Implement a **new xchats Postgres reader** with the same interface: `Window` = last ~15 `xchats.messages` rows for the thread (mapped to `domain.Message{Role: customer if direction='in' else agent, Content, ...}`); `Profile` = `xchats.contacts.attributes` (+ thread `stage`/`history_state` → so the brain sees `context_state`). |
| Draft persistence (submodule writes a Chatwoot private note) | The caller (a `process_event` → `ai_draft` worker job) takes the returned `Draft` and **inserts an `xchats.ai_drafts` row** + emits the realtime `ai_draft.created`. Escalation / `PricingError` / low confidence map to draft flags — **not** a note. |
| Config/snapshot store (`internal/infrastructure/sqlite/*`) | Reimplement on **Postgres** using `xchats.ai_snapshots` / `xchats.ai_topics` / `xchats.ai_assets` / `xchats.ai_prices` / `xchats.ai_audit_log` (see `9-database-schema.md`). Keep the publish/rollback/dedup semantics. |

- `internal/usecase/whatsapp/*`, `internal/ports/http/admin/.../whatsapp.html` — Chatwoot-flavored Evolution provisioning (xchats has its own accounts/QR manager).

## Wiring in xchats

- **Trigger (v1 = on-demand):** the member presses **"Suggest reply"** → the API enqueues an
  `ai_draft` job → `HandleMessage(window, profile, snapshot)` → writes `xchats.ai_drafts` →
  `ai_draft.created`. (Auto-draft on every normalized inbound from the `process_event` worker is a
  deferred fast-follow — keep the job decoupled so the trigger is just a different caller.)
- **One pending draft per conversation:** enforce with a `UNIQUE` partial index (one `suggested`
  draft per conversation) and/or a per-conversation Postgres advisory lock — **not** the submodule's
  in-process `keyedMutex`, which serializes nothing across worker processes. Approve is idempotent
  (conditional `UPDATE … WHERE draft_state='suggested'`; a newer inbound supersedes — see
  `7.1-endpoints.md`, `9-database-schema.md`).
- **Auto-send gate (deferred — Phase 4D):** v1 does **not** build the auto-send path. The
  `respond_mode` column defaults `NEVER` and stays; `CONFIGURE_TIME|ALWAYS` and their send path are
  Phase 4D, behind confidence + golden-gate preconditions (`escalate=false`, `PricingError=false`,
  `confidence ≥ threshold`, active snapshot passed the golden gate).
- **Don't draft on incomplete context:** while `history_state` is `syncing/partial`, mark the draft
  `context_state` accordingly (the brain already accepts this signal).

## Port gate (done when)

v1 (Phase 4A):
- `go test ./internal/assistant/...` passes after the module-path rewrite (the submodule's
  `brain_test`/domain tests are the parity check).
- A seeded Snapshot loads from `0002_seed.sql`/markdown on boot (no admin UI).
- Pressing **Suggest** on an inbound fixture (`captures/`) produces an `xchats.ai_drafts` row + an
  `ai_draft.created` event end-to-end.
- **Against a non-empty seeded Snapshot**, the fixture produces a **grounded** draft (not an
  escalation) and an off-KB question correctly escalates — i.e. quality, not just plumbing. A bare
  escalation row does **not** satisfy the gate.
- The golden-set deterministic metrics pass offline (`8.7-ai-evals.md`).

Deferred (Phase 4B): a `Playground` call returns a `Draft` from a Postgres-loaded snapshot, and
`POST /assistant/publish` enforces the quality gate (price-safety / asset-precision) at publish time.
