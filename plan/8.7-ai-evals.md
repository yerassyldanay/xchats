# AI Assistant — Evals & Quality Gate

> ⚠️ **Amended by [`14-draft-staging-and-retrieval.md`](14-draft-staging-and-retrieval.md).** The runtime
> prose grounding judge is **deferred from v1** (human review covers prose until then; mandatory before
> auto-send). The deterministic metrics and the fact-safety gate ship in v1 unchanged. 14 wins on conflict.

How we know the assistant's drafts are **good**, not just that the pipeline runs. This is the
regression net for every persona / KB / prompt / model change, and the **publish gate** for a new
snapshot. Ported from the working brain's design (`examples/repos/xpayment-crm/docs/07-testing-and-evals.md`),
which xchats had previously dropped on the floor.

> Why this exists: the brain answers **only** from the published KB and **escalates** on any gap
> (see `8.4-ai-assistant-knowledge-base.md`, `8.1-ai-assistant-prompt.md`). So draft quality is a
> direct function of KB coverage, and a structurally-valid `xchats.ai_drafts` row can still be a
> useless escalation. Mechanical "a row was produced" tests (`8.6-port-checklist.md`,
> `0.1-definition-of-done.md` Phase 4) do **not** measure this. The eval set does.

## The golden set

A small set of **real cases** (20–40 to start), checked into git, mined from real conversations
(the same mining that seeds the KB — see `8.4` and the Phase-4 seeding step in
`0.1-definition-of-done.md`). Each case:

```jsonc
{
  "name": "growth_tariff_price_ru",
  "window": [ { "role": "customer", "content": "Сколько стоит тариф growth?" } ],
  "profile": { "interested_tariff": "growth" },
  "expect": {
    "must_include": ["{{tariff.growth.price}}"], // rendered fact token must appear
    "must_exclude": ["1990", "2990"],         // no hand-typed digits leaking past the token system
    "asset_refs": ["price_list_pdf"],          // expected catalog refs (precision/recall vs actual)
    "reply_language": "ru",
    "escalate": false
  }
}
```

## Metrics (run order: deterministic first, judge last)

**Deterministic (no live LLM — run offline against stubbed/recorded drafts):**

- **fact-safety (number check)** — every fact token `{{table.slug.field}}` renders to its stored column
  value for the reply language, **and every currency-/unit-adjacent number in the draft traces back to an
  injected value**; **no bare digits** that should have been a token. This is the deterministic backstop
  from Decision 4 (numbers are guarded deterministically, never by the judge). **Target: 1.0 (hard).**
- **asset-ref precision / recall** — `asset_refs` vs expected; no hallucinated/unknown refs survive
  (`ResolveAssets` already drops them). **Target: precision ≥ 0.9.**
- **language match** — `reply_language` correct (RU→`ru`, KK→`kk`, mixed→`ru`); see the deterministic
  cross-check in `8.6-port-checklist.md`.
- **escalation correctness** — `escalate` matches expectation (escalates when KB-gap, answers when covered).
- **must-include / must-exclude** — required phrases present, forbidden ones absent.

**LLM-as-judge (live, deferred to nightly/manual — off the PR path):**

- A 1–5 rubric on tone/helpfulness/grounding. **Target: mean ≥ 4.0.** Costs a key + tokens, so it is
  **not** a gate on every commit; it runs nightly or on demand, matching the source's stance.
- This offline rubric is the analogue of the runtime **prose grounding judge** (Decision 4): a separate,
  cheap model that checks every **non-numeric** claim is supported by the injected topics, **biased to
  escalate** — on doubt or error it defers to a human, never auto-approves. Prose is guarded by the judge;
  numbers by the deterministic check above.

## The publish gate

`POST /xchats/api/v1/assistant/publish` (see `7.1-endpoints.md`) runs the **deterministic** metrics
against the candidate snapshot before swapping it live. Publish is **refused** unless:

- **fact-safety = 1.0** (every fact token resolves to a column value for each required language, and the
  number check passes), and
- **asset-ref precision ≥ 0.9** (configurable in `config.yaml`).

The LLM-as-judge mean is **reported** at publish time but does not block (it requires a live call).
Thresholds live in `config.yaml` so they are tunable without code.

## How it runs

- Deterministic metrics live behind a `//go:build eval` tag in the Go backend and run against the
  **Fake LLM** (recorded `emit_draft` outputs) — so the offline half needs no network and runs in the
  isolated harness (`6-isolated-testing.md`). This is the part that gates publish and CI.
- The live judge run is a separate `make eval-judge` target requiring `LLM_API_KEY`.

## Scope for v1

- **In v1:** the golden set + deterministic metrics + the fact-safety/asset-precision publish gate.
  This is cheap, offline, and gives a regression net the moment the KB is non-empty.
- **Deferred:** the LLM-as-judge prose scoring on the PR path (keep it nightly/manual); calibrating a
  numeric **auto-send** confidence threshold (that gate belongs to Phase-3 auto-send — see
  `8.6-port-checklist.md` "Auto-send gate").
